# Attune RAG Evaluation Assets

Date: 2026-07-23

Status: Implemented registry contract

Registry: `tests/eval/assets/public_knowledge_assets.json`

## Goal

The RAG evaluation framework must validate whether Attune can support typical
knowledge-base conversations across real-time Q&A, operation guidance,
decision assistance, summary, multiturn follow-up, and scale regression. The
asset design makes every data source explicit: what repository or snapshot is
used, how it is pinned, whether it can be redistributed, what questions it
must answer, what sources should be cited, and what accuracy/latency threshold
blocks a release.

## Asset Tiers

- `T0`: generated fixtures committed to this repo. Used by PR CI and local
  development. No external fetch and no copyright ambiguity.
- `T1`: small public references. Suitable for hosted CI when download time is
  acceptable.
- `T2`: single-industry thousand-document repositories or generated corpora.
  Used by K3/nightly/release gates. A T2 suite must not combine several
  industries to reach 1,000 documents.
- `T3`: single-industry ten-thousand-document stress and convergence suites.
  Used by weekly and release-candidate hardware gates. Cross-industry mixed
  corpora are allowed only as routing/drift专项, not as scale acceptance.

## Redistribution Policy

- `vendored_generated_only`: synthetic fixtures may be committed and packaged
  only when they are generated by Attune tests.
- `redistributable_reference`: source license is clear enough for evaluation
  references and reports. Reports still cite upstream source and commit.
- `external_fetch_only`: upstream is public but license is undefined, missing,
  or mixed. CI may fetch it on controlled evaluation hosts, but Attune must not
  redistribute the documents, chunks, vector DB, or packaged derived assets.

This separates Attune delivery from evaluation data. The `.deb` and capability
packs remain clean; large or ambiguous corpora are operator-fetched test inputs.

## No-OCR Public Corpus Policy

Until K3 OCR stability work is complete, release-scale RAG gates should prefer
source formats that can be parsed without image OCR:

- Software documentation repositories with Markdown, reStructuredText, SGML, or
  static HTML source. Priority candidates are Kubernetes website docs, Linux
  kernel `Documentation/`, PostgreSQL `doc/src/sgml`, OWASP Cheat Sheet Series,
  Prometheus docs, and Rust Book.
- GitBook-style manuals and product handbooks are preferred when the site can
  be materialized through sitemap/HTML/Markdown export into normalized text
  files. Each GitBook candidate must be fetched as a single product or industry
  corpus, not mixed with other products to satisfy scale targets.
- Engineering and mechanical references only when the upstream publishes HTML,
  Markdown, or PDFs with a reliable text layer. NASA Systems Engineering
  Handbook is acceptable as an engineering-domain starter; scanned maintenance
  PDFs stay out of release gates until OCR is stable.
- Generated PDFs are allowed only when they are produced from text/HTML source
  during materialization, so the resulting PDF has an embedded text layer and
  does not require OCR.

The default large-scale path is therefore: fetch pinned public text source,
materialize normalized Markdown plus optional text-layer PDF copies, bind the
single-industry directory, wait for `pending_embeddings=0`, then run search,
chat, summary, multiturn, negative-evidence, and latency gates.

For the current K3 release cycle, prefer large software documentation or web
book style corpora over scanned manuals. Mechanical or engineering suites are
allowed only when the selected source can be normalized from HTML/Markdown or
from PDFs with an embedded text layer; OCR-dependent assets are excluded from
blocking E2E until the scheduler OCR path is stable.

## GitBook and Public Manual Asset Standard

GitBook-style product manuals are strong candidates for Attune because they are
large, professional, and mostly HTML text. The standard materialization path is:

1. Fetch the root page, sitemap, and linked pages under the same GitBook space.
2. Convert each page to normalized Markdown with title, canonical URL, breadcrumb,
   language, fetch time, and content hash.
3. Store one page per file under a single-domain corpus directory.
4. Generate a manifest with page count, byte size, expected chunks, language mix,
   fetch errors, and excluded URLs.
5. Bind only that product/industry directory into Attune and run the single-industry
   suite.

GitBook release gates must include:

- `real_time_qa`: exact product/manual fact lookup.
- `operation_guidance`: procedural user support with cited steps.
- `decision_assistance`: evidence-first comparison or recommendation when the
  manual supports it.
- `summary`: per-topic/source summary that requires `rag_intent_plan` per-topic
  coverage for multi-topic questions.
- `negative_evidence`: refusal or evidence-gap answer when the manual does not
  support a requested product, policy, or medical/clinical decision.

## Expected Results

Each asset defines expected questions, sources, required terms, and metrics in
the registry. The runner must evaluate outputs at three levels:

1. Retrieval result: `/api/v1/search` must return the relevant document or
   source family in top 5.
2. Grounded answer: `/api/v1/chat` must include required source terms and must
   cite expected source labels. Summary cases are still routed through the
   Chat RAG surface when the user asks for a knowledge-base summary.
3. Release threshold: suite-level metrics must stay above minimum accuracy and
   below maximum latency. Violations are reported as `failure_layer=threshold`.

Representative expected outputs:

- TCP/IP origin questions cite `tcpip_origin` or RFC source files and include
  ARPANET/DARPA evidence.
- TCP/IP troubleshooting questions cite troubleshooting/support workflow
  sources and include physical link, IP, route, DNS, port/firewall, packet
  capture, and logs.
- Aviation/manual questions cite manual file/section/page identifiers and
  avoid operational flight instructions.
- Mechanical design questions cite the relevant volume/section and refuse final
  design sign-off when the evidence is insufficient.
- OWASP questions cite specific cheat sheets and include control families such
  as work factor, allowlist, metadata-service blocking, and session ID handling.
- Kubernetes questions cite docs paths and include Pod, Event, Deployment,
  Service, and `kubectl describe` evidence.
- RISC-V questions cite ISA/privileged/unprivileged sources and distinguish ISA
  support from deployed scheduler performance.
- Prometheus questions cite docs on scraping, alerting, querying, and
  configuration before recommending a PromQL or alert-rule change.
- Rust Book questions cite chapter paths and include ownership, borrowing,
  lifetimes, traits, and compiler-error evidence.

## Single-Industry Scale Rule

Every scale suite validates one industry at a time. The corpus domain,
scenario domain, expected sources, noise documents, and near-duplicate
distractors must all stay inside that industry. This prevents a false pass
where networking, security, product, and mechanical documents are combined to
reach a thousand-document count while no single industry knowledge base is
actually large enough.

Current scale acceptance defaults:

| Suite | Industry | Corpus | Documents | Required coverage |
| --- | --- | --- | ---: | --- |
| `k3_rag_scale_thousand` | security | `security_generated_thousand_docs` | 1000 | fact lookup, operation guidance, decision assistance, summary, multiturn, negative evidence |
| `k3_rag_scale_ten_thousand` | security | `security_generated_ten_thousand_docs` | 10000 | fact lookup, operation guidance, decision assistance, summary, multiturn, negative evidence, near-duplicate/citation-stability stress |

## Precision and Response Targets

Default acceptance targets are intentionally stricter for small deterministic
fixtures and slightly looser for large long-text corpora:

| Tier | Retrieval Hit@5 | Citation Hit Rate | Answer Accuracy | Hot Chat p95 | Longtext Chat p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| T0 | 1.00 | 1.00 | 0.90 | 30000 ms | not used |
| T1 | 0.90 | 0.90 | 0.85 | 30000 ms | 45000 ms |
| T2 | 0.85-0.90 | 0.90 | 0.80-0.85 | 30000-60000 ms | 60000 ms |
| T3 | 0.85 | 0.90 | 0.80 | 30000 ms | 60000 ms |

For release gates, a failed turn and a threshold failure are both blocking, but
they mean different things:

- Failed turn: the answer itself missed required evidence, citations, or safety
  boundaries.
- Threshold failure: aggregate quality or latency regressed even if individual
  checks did not all fail.

The `terminal_error_rate` denominator is failed turns, not failure records, so
multiple assertions on one answer cannot inflate the rate above 1.0.

## Gaps That Remain Explicit

- The generic live runner currently directly materializes generated Markdown
  corpora. Full automatic materialization of every external asset in this
  registry is the next implementation slice.
- External-fetch-only corpora need per-host cache directories and cleanup
  rules before they are enabled in hosted CI.
- Aviation and mechanical design assets are suitable for controlled evaluation
  only until legal review approves broader redistribution.
